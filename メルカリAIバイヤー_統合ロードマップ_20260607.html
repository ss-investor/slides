1. 核心の論点：ISBN紐付けとLLM照合を「どう統合するか」

現状の紐付けパイプライン（問題点）

スクレイパー（mercari_continuous 等） └─ タイトル/説明文を正規表現でISBN抽出 ├─ ISBN見つかる → book_products.isbn_13 で照合 → listings.asin に保存 ✅ └─ ISBN無し → その場で破棄（continue） ❌ ← mercari_fullscan.py:203 （NDL補完=タイトル→ISBNは和書7サイトのみ・ヒット率約6%）
＝個人出品（メルカリ等）の大半は識別できず捨てられている。これが今回埋める「宝の山」。

あるべき統合パイプライン（2段紐付け）

スクレイパー └─ 第1段：正規表現ISBN抽出 → 見つかれば従来通り照合（速い・確実）→ listings.asin ✅ └─ ISBN無し → 破棄せず保持 → LLM識別キューへ ↓ 第2段：ローカルLLM識別サービス（価格フィルタで安い候補に限定） ① 写真+タイトルを vl:7b で識別（書名/著者/種別） ② 照合エンジン（正規化+著者+コアタイトル+pg_trgm）→ 候補ASIN+信頼度 ③ 詳細ページのバーコードを読めれば ISBN/JAN で完全一致＝誤マッチゼロ ④ 結果を listings の LLM列（or 専用テーブル）に保存 ↓ 第3段：買い判定デーモン（Keepa統計 + 14b + 決定論floor） → buy/conditional/skip/trap + 利益 + 理由 → buy_verdict テーブル ↓ ポータル：「今日の買うべきリスト」+ /books等にAI推定バッジ + 人間レビュー
⚠️ 統合の設計原則（ここを外すと事故る）
  • ISBN確定 > LLM推定：正規表現/バーコードで確定したISBNは絶対優先。LLM推定がそれを上書きしない。
  • 権威列を汚さない：LLM推定は listings.asin に直書きせず、別列（llm_asin / llm_confidence / barcode_status）に置く。 「高信頼 or バーコード一致」のみ asin へ昇格（promotion rule）。誤マッチが本番表示に混ざらない。
  • NDLパターンを踏襲：ndl_queried_at と同じく llm_queried_at で処理済み管理（再処理・冪等・キュー化が楽）。
  • 価格フィルタを先に：全listingにLLMを回さず「Keepa相場より十分安い＝黒字になりうる」候補だけに限定（DVD構築のstats-only先行と同思想）。
  • 削除運用の見直し：ISBN無し紐付け不能listingの定期削除は、LLM識別を一巡させてからに変更（消す前に拾う）。
  • NDLはLLMの下位互換：和書タイトル→ISBNのNDL補完は残しつつ、LLMが画像で上位互換（海外/コード無しもカバー）。役割を整理。
⚠️ 「LLMで処理する」対象には2種類の入口がある（混同注意・2026-06-07追記）
区分状態詰まりの原因LLMの役割
①コード無し
(メルカリ等 個人出品)		ISBNが全く無いコードが読めない写真+タイトルでゼロから商品特定→Keepa照合。バーコード写りで完全一致(誤マッチゼロ)。実測識別94.7%
②絶版/未掲載
(例: 紐付け待ち9,203種ISBN)		ISBNは有るがAmazon/Keepaに無いその版がAmazonカタログに不在(コードは読めている)exact逆引きは0。あいまいタイトル照合で同じ本の別版ASINを救済(画像は確認用・既にタイトルがあるので画像無しでも可)。別版も無ければ他販路で評価 or 対象外
→ 別ターミナルの「紐付け待ち9,203件(全体0.36%)＝Amazonに無い絶版ISBN」は②。これらをLLMに委ねるのは正しいが、仕事は〈コード読取〉でなく〈別版救済＋他販路評価〉。①(画像識別)とは入口が違う。逆引きdaemonの exact照合の後段として、あいまい照合層を置く位置づけ。

1.5 データ投入とLLM判定の「タイミング」（非同期エンリッチ）

結論：ポータルへは先に入れる。LLMは定期実行で後からバッジ/フラグを付与する（"判定完了を待ってから投入"ではない）。
理由＝既存のNDL補完(ndl_queried_at)・候補制限チェック・MV更新と同じ非同期パターン。LLMは1件5〜20秒と遅く、取り込みをブロックすると全体が詰まる。分離すればスクレイピングは全速・LLMは自分のペースで追従。
listing投入（即・ポータルに表示 / ISBN無しも破棄せず保持） 状態=未処理 │ ▼ 定期ワーカーA（識別・照合 / 価格フィルタで安い候補のみ） ISBN確定 > 無ければLLM識別 → 照合(pg_trgm/著者/コアタイトル) → バーコード確認 → llm_asin / llm_confidence / barcode_status を別列に付与（権威のasinは汚さない） 状態=AI推定済🏷️ │ ▼ 定期ワーカーB（買い判定 / Keepa + 14b + 決定論floor） drops365・avg365・利益を統合 → buy / conditional / skip / trap 状態=判定済🏷️ │ ▼ ポータル：「買うべき順」リスト + 高信頼/バーコード一致はasinへ昇格（既存の集計・利益判定に自動合流） 低信頼は人間レビュー行き（本番表示を汚さない）
状態遷移：未処理 → AI推定済(識別バッジ) → 判定済(買い/見送りバッジ)
per-itemの依存だけ正確に：利益判定(B)はASINが要るので必ず識別・紐付け(A)の後に回る＝Phase2→Phase3の順序は正しい。ただし両方とも「既にあるlistingに後から重ねる」非同期処理で、判定完了までポータル投入を待たない。ISBN確定組は従来通り即フル表示。

1.7 収集戦略の転換：「ISBN中心」→「広く取る」（2026-06-07追記）

LLMが識別できるようになった以上、ヤフオク/メルカリ等は「ISBN付きだけ」でなく、カテゴリ/キーワードで広く収集できる。
【従来】 キーワード/ISBN検索 → ISBN付き出品だけ保持（コード無しは破棄）＝個人出品の大半を取りこぼし 【今後】 カテゴリ/キーワードで広く収集（コード無しも保持・image_url含む） → LLM識別パイプラインへ ※ ただし全件LLMは非現実的 → 収集 or 投入時に価格フィルタ（Keepa相場より十分安い＝黒字になりうる帯）で絞る
トレードオフ（必ず設計で握る）：①収集量が激増→Mercari/ヤフオクのWAF・レート管理が一段重要（continuousとの協調・巡回間隔）②listings肥大→価格フィルタ＋識別不能の長期パージ③従来のISBN検索パスは"既知の良書を速く拾う"用途で併存させる価値あり（広域sweepと二本立て）。

1.8 LLMパイプライン＝【識別】＋【判定】の2段。既存ISBN在庫は判定だけ回す（2026-06-08追記）

LLMバイヤーは2つの工程に分かれる：① 識別（写真＋タイトルからASINを特定）＋ ② 判定（Keepa統計＋14bで買い/見送り＋利益・ヤフオクは入札上限）。
コード無し品（メルカリ/ヤフオクの個人出品・ISBN無し）＝①識別＋②判定の両方が必要（ASINが不明なので識別で繋ぐ） 既存ISBN在庫（ゲーム/DVD/ヤフオク/古本＝ASIN確定済み）＝②判定だけでよい（識別は不要・スキップ）
現状のギャップ（ここが今回の追記の肝）：既存ISBN在庫は確定的な利益足切り（book_summary_mv→/books・/games・/cd-dvd の黒字候補表示）とオンデマンドのClaude買い判定（buy-chat・🤖AI推奨価格ボタン）は動いているが、ローカル14bの自動買い判定は未実装（今はコード無しワーカーの中だけ）。＝「既存ISBN在庫にも自動でAI買い判定」はこれから作る。
実装方針：識別を飛ばし、ASIN確定済み在庫に対して Keepa統計→ローカル14b判定（決定論floor＋理由＋red_flags／ヤフオクはmax_bid_jpy入札上限も）を回して保存する「判定だけデーモン」（下記 P3-6）。既存 buy_judge（識別後の判定半分）をそのまま再利用でき、重い画像識別が不要なので軽い。範囲（全ASIN在庫か／黒字足切り通過分だけか）は要相談（全件は Ollama 時間＋Keepa トークンを食うため、まず黒字候補に絞るのが現実的）。
参考：ヤフオクのLLMバイヤー（入札制ゆえ入札上限価格 max_bidを再販相場から逆算）は 2026-06-08 に実装済（隔離テーブル yahoo_auctions_llm_match／ワーカー yahoo_llm_worker.py／ポータル /yahoo-auctions-ai）。この「判定だけデーモン」は同じ判定ロジックを既存ISBN在庫にも横展開するもの。

5. リスクと対策

リスク対策
誤マッチで間違った商品を仕入れる（最大の事故）権威asinと分離＋信頼度ゲート＋バーコード照合＋人間レビュー。低信頼は仕入候補に出さない。
言い値相場の罠（高値出品に吊られる）判定はavg365基準＋drops365=0はskip（PoCでMR.BIG捕捉済）。
Mercari WAF / 二重巡回ブロックcontinuousとbootout協調 or 別時間帯。詳細収集はレート遵守・flock多重起動ガード。
Keepaトークン枯渇価格フィルタで判定対象を絞る＋キャッシュ＋日次上限＋既存daemonと予算分配。
listings肥大（no-ISBN保持で件数増）価格フィルタで保持/識別対象を限定。識別不能の長期放置分は定期パージ。
7Bの判定ノイズ判定は14bへ分離済（PoCで改善確認）。floorは決定論で死守。
本番DB変更（pg_trgm）の影響後方互換の拡張・索引のみ。検証環境/低負荷時間に適用。承認制。
